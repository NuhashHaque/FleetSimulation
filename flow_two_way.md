### Flow 1: Command Lifecycle (User $\rightarrow$ Simulator & Databases)

This flow tracks what happens when a user issues an instruction (like clicking "PAUSE" for Bus 1) and how that creates an immutable audit trail.

1. **User Action (React UI):** The user clicks the "PAUSE" button. The React frontend sends an HTTP `POST` request (e.g., `/api/vehicles/BUS_01/command` with payload `{"action": "PAUSE", "user_id": "admin_1"}`).
2. **Reverse Proxy (Nginx):** Nginx intercepts the HTTPS request on Port 443, handles the SSL termination, and proxies the request to the internal FastAPI backend.
3. **API & Message Production (FastAPI):** * FastAPI receives the request and validates the payload.
* It acts as a Kafka Producer, publishing the command JSON directly into the Kafka topic named `fleet-commands`.
* FastAPI immediately sends an HTTP `200 OK` response back through Nginx to the React UI (making the UI feel instantly responsive).


4. **Device Execution (Python Simulator):**
* The Simulator runs a dedicated Kafka Consumer thread listening to `fleet-commands`.
* It pulls the "PAUSE" message.
* The specific thread managing `BUS_01` intercepts the command, updates its internal state machine to `PAUSED`, and halts its interpolation (movement) math.


5. **Audit Logging (Postgres ETL Worker):**
* Simultaneously, a separate Python ETL script (acting as another Kafka Consumer) pulls that exact same message from `fleet-commands`.
* It maps the JSON to a SQL query and inserts a new row into the **PostgreSQL** `command_audit_log` table. This permanently records who sent the command, to which bus, and at what exact timestamp.

### Flow 2: Live Telemetry Lifecycle (Simulator $\rightarrow$ User & Databases)

This flow tracks a single 1Hz physical location update generated by the bus, showing how it updates the live map and populates both databases simultaneously.

1. **Data Emission (Python Simulator):** The Simulator thread for `BUS_01` calculates its new GPS coordinate based on speed and time. It publishes a JSON payload to the **Mosquitto MQTT Broker** on topic `fleet/bus/BUS_01/telemetry`.
2. **Edge-to-Stream Bridge (MQTT-to-Kafka Script):**
* A lightweight Python bridge script is subscribed to Mosquitto.
* It instantly receives the MQTT payload and acts as a Kafka Producer, pushing that raw JSON into the Kafka topic named `raw-telemetry`.


3. **Live Map Update (FastAPI to React UI):**
* The **FastAPI Backend** continuously consumes the `raw-telemetry` Kafka topic.
* Upon receiving the new GPS tick, it immediately broadcasts the data over an open WebSocket (or SSE) connection through Nginx to the React UI.
* The React UI receives the data and updates the CSS state, moving the bus icon slightly forward on the progress bar.


4. **Time-Series Storage (InfluxDB ETL Worker):**
* A dedicated Python ETL script consumes the `raw-telemetry` topic.
* It parses the high-frequency metrics (`latitude`, `longitude`, `speed_kmh`).
* It writes this data point into **InfluxDB**, which is optimized to store millions of these rapid-fire 1Hz ticks for later graphing.


5. **Event Storage & Filtering (Postgres ETL Worker):**
* The Postgres ETL script also consumes the `raw-telemetry` topic, but it does not save every 1Hz tick. It applies a **Filter**.
* It checks the JSON state. *Did the `trip_count` increment? Did the status change from `RUNNING` to `LAYOVER`?*
* If an event occurred, it writes a structured record into the **PostgreSQL** `trip_logs` or `status_history` tables. If nothing changed except the GPS location, it ignores the message and moves to the next one.
